# V2 — Platform features

> **Status:** not started
> **Depends on:** Phases 1–6 (a deployed, working V1)
> **Goal:** turn a working product into a platform.

V1 proves the architecture with four services and one user type. V2 is
where Agent Hub stops being *your* integrations and becomes something
users extend themselves.

**Do not start any of this before V1 is deployed and someone real is
using it.** Every item here is a bet on demand you have not measured
yet.

---

## Priority order

Ranked by value delivered per unit of work:

```text
1. Custom MCP servers    ← highest leverage, unlocks everything else
2. Agent memory          ← biggest quality jump for existing users
3. Workflows             ← the "why we bought it" feature for teams
4. Scheduling            ← small, high perceived value
5. Marketplace           ← only worth it once 1 and 3 exist
```

# V2.1 — Custom MCP servers ⭐

The single most powerful feature on this list. It changes the answer
to *"does it integrate with X?"* from "not yet" to "yes, if X speaks
MCP."

```text
Add MCP Server

  Name         My Company CRM
  Transport    HTTP / SSE
  URL          https://crm.example.com/mcp
  Auth         OAuth | API key | none

  [Test connection]  →  found 23 tools

  [Add server]
```

## Why Phase 2 already supports this

```python
# agent/discovery.py
namespace = self._detect_namespace(name, meta)
#   1. explicit metadata (namespace / service / provider)
#   2. known prefix convention  ← fallback for YOUR server
```

Metadata wins over convention, precisely so a third-party server that
does not follow your `github_` naming still gets classified.

```python
# agent/classification.py
operation, source = classify_operation(name, namespace, annotations)
#   1. override → 2. MCP annotations → 3. verb → 4. fail closed
```

A well-behaved third-party server sends `readOnlyHint` and
`destructiveHint`, so classification is **authoritative** rather than
guessed — better than for your own server today.

## What actually needs building

```text
mcp_servers                        (per user or per organisation)
  id, owner_id, name
  transport        stdio | http | sse
  url, auth_type
  credentials_enc
  status           connected | error | disabled
  tool_count, last_discovered_at
```

```text
1. Transport abstraction beyond stdio (Phase 3 Problem 1, Option C)
2. Discovery on demand + refresh
3. Namespace collision handling (two servers both exposing `search`)
4. Per-server tool limits (a 500-tool server must not swamp routing)
5. Sandboxing / egress rules for untrusted servers
6. Health checks and automatic disable on repeated failure
```

## The security problem to solve first

A custom MCP server is **code you did not write, receiving your users'
requests**. Before shipping this:

```text
- run it out-of-process, never in the API process
- network egress allowlist
- hard timeouts and payload size caps
- treat every tool description as untrusted text (it reaches the LLM)
- never auto-enable tools from a newly added server
```

That last one matters: tool descriptions are prompt input. A hostile
server can put instructions in a description.

# V2.2 — Agent memory

Today every conversation starts blank and long conversations overflow
the context window. Memory fixes both.

## Four kinds, in order of value

```text
1. CONVERSATION SUMMARY     cheapest, biggest immediate win
   Summarise older turns, keep recent ones verbatim.
   Fixes: long conversations breaking.

2. USER PREFERENCES         explicit, small, reliable
   "Always use the argus/test repo." "Answer briefly."
   Fixes: repeating yourself every session.

3. PROJECT CONTEXT          per agent, curated
   Repo names, channel ids, folder ids the agent works with.
   Fixes: entity lookup on every turn.

4. SEMANTIC RECALL          most complex, least certain payoff
   pgvector over past conversations and tool results.
   Fixes: "what did we decide about X last month?"
```

**Build 1 and 2 first.** They are simple, and they solve the problems
users actually complain about. Vector search is fashionable and is the
last one you need.

```text
agent_memories
  id, agent_id, user_id
  kind          summary | preference | context | fact
  content, embedding VECTOR(768) NULL
  source_message_id, confidence
  created_at, expires_at, last_used_at
```

## Rules that keep memory from making things worse

```text
1. Memory is CONTEXT, never INSTRUCTION. Inject it as data.
   Otherwise a remembered sentence becomes a prompt injection you
   stored yourself.
2. Show the user what is remembered, and let them delete it.
3. Expire unused memories.
4. Never store credentials or secrets - reuse the Phase 2.8
   redaction list.
5. Cap injected memory as a fraction of the context window.
```

# V2.3 — Workflows

```text
Trigger:  GitHub PR opened
    ↓
Step 1:   Analyze the PR              (agent)
    ↓
Step 2:   Search Drive for the spec   (tool)
    ↓
Step 3:   Generate a review           (agent)
    ↓
Step 4:   Approval                    (human)
    ↓
Step 5:   Post to Slack               (tool)
```

```text
workflows
  id, owner_id, name, definition JSONB, enabled, version

workflow_runs
  id, workflow_id, trigger_payload JSONB
  status         pending | running | waiting_approval | succeeded
                 | failed | cancelled
  started_at, finished_at

workflow_steps
  id, run_id, step_index, step_type
  status, input JSONB, output JSONB, error JSONB
  execution_id → tool_executions      ← reuses Phase 2.8
```

## What this really is

A **durable state machine**. The interesting problems are not the UI:

```text
- resuming after a restart (a run may span days if a human is slow)
- exactly-once semantics for writes
- retries that respect the Phase 2.7 two-tier rule
- cancelling a run mid-flight
- versioning: a running workflow must finish on the definition it
  started with
```

Do not hand-roll the engine. Use Temporal, Prefect, or Celery with an
explicit state table. A homegrown durable executor is a year of work
and you will get exactly-once wrong.

## Triggers

```text
manual        a button. Build this first.
scheduled     cron. Second.
webhook       GitHub / Slack events. Third - needs signature
              verification and replay protection.
```

# V2.4 — Scheduling

Small feature, high perceived value.

```text
Every weekday at 09:00
  → "Summarise yesterday's commits and post to #standup"
```

```text
scheduled_tasks
  id, agent_id, user_id
  cron_expression, timezone       ← store the timezone, always
  prompt, enabled
  last_run_at, next_run_at, last_status
```

```text
- store IANA timezones, never fixed offsets (DST exists)
- overlap policy: skip / queue / cancel-previous
- a scheduled run has no human present → approval must AUTO-DENY
  unless the user pre-approved the specific tools
- always notify on failure; nobody watches a silent scheduler
```

That third rule follows directly from Phase 5: **silence is not
consent.** An unattended run must not be able to approve itself.

# V2.5 — Plugin marketplace

Build this **last**. A marketplace with three plugins is a list.

```text
Marketplace                              [Search]

  GitHub          18 tools    ★ 4.8    Installed
  Google Drive    13 tools    ★ 4.6    Installed
  Notion          22 tools    ★ 4.5    [Install]
  Jira            31 tools    ★ 4.2    [Install]
```

```text
marketplace_plugins
  id, key, name, description, icon_url
  developer_name, verified
  latest_version, install_count, rating
  mcp_config JSONB, required_scopes TEXT[]

plugin_versions
  id, plugin_id, version, changelog
  tool_manifest JSONB, published_at, deprecated_at
```

Prerequisites, in order:

```text
1. V2.1 custom MCP servers    (the runtime)
2. A review process           (who verifies a plugin is safe?)
3. Versioning + upgrade path  (a plugin removing a tool breaks agents)
4. Enough demand to justify all of it
```
