## The three problems that shape everything ahead

These come from the **actual current code**, not from theory. Each is
covered in detail in the phase that solves it.

### 1. The MCP session cannot be per-request

`ai_client.py` spawns `python server.py` as a subprocess and holds it
for the whole CLI session. In a web server, one subprocess per request
does not work. → **[Phase 3](Phase3.md), Problem 1**

### 2. The MCP server is single-tenant

```python
self.token = os.getenv("GITHUB_TOKEN")   # ONE token, for everyone
```

Every Agent Hub user would share one GitHub account. → **[Phase 5](Phase5.md)**

### 3. Approval cannot block

`ConsoleApproval` calls `input()`. A web request cannot wait ten
minutes for a human, so the agent turn has to become suspendable.
→ **[Phase 3](Phase3.md) design, [Phase 5](Phase5.md) implementation**

## What Phase 2 already gives the later phases

Phase 2 was built with seams so the rest is addition, not rewriting:

| Phase 2 artefact | Used by | For |
|---|---|---|
| `ExecutionRecord.to_dict()` | Phase 3 | the `tool_executions` table, unchanged |
| `RoutingDecision.to_dict()` | Phase 3 | `messages.routing` + debugging |
| `PermissionPolicy` protocol | Phase 5 | `DatabaseScopePolicy` — executor untouched |
| `ApprovalHandler` protocol | Phase 5 | `WebApproval` — executor untouched |
| `tool.permissions` scopes | Phase 5 | per-agent grants, wildcard-aware |
| `operation` + `risk_level` | Phase 4 | grouping and badges in the tool picker |
| `RECOVERY_HINTS` | Phase 4 | human-readable failure messages |
| `EmbeddingProvider` seam | V2 | semantic routing at 300+ tools |
| Annotation-first classification | V2 | third-party MCP servers classify correctly |

> **The pattern worth copying:** define the small interface early, ship
> a trivial implementation, swap it later. Every row above is a swap,
> not a migration.

## Conventions in these documents

```text
⭐              the part of the phase that matters most
⚠️              a trap that is expensive to discover late
"NOT build yet" scope discipline - resist these
"milestone"     testable acceptance criteria, not opinions
```

Every phase ends with a numbered build order. Follow it — the ordering
encodes dependencies that are not obvious from the feature list.
