# V3 — Scale and ecosystem

> **Status:** speculative
> **Depends on:** V2, and real usage data
> **Goal:** the things that only make sense once many people depend on
> the product.

Everything here is a **bet**. Do not treat this document as a plan —
treat it as a list of options to reach for when a specific problem
appears.

> The most common way ambitious projects die is building V3 before
> V1 has users.

# V3.1 — Multi-agent systems

```text
                  Manager Agent
                        │
         ┌──────────────┼──────────────┐
         ▼              ▼              ▼
    Developer      Researcher       Reviewer
      Agent          Agent           Agent
         │              │              │
      GitHub          Drive          GitHub
```

## When this is worth it

```text
✓ tasks genuinely decompose into independent subtasks
✓ subtasks need different tools, prompts, or models
✓ one agent's context window is the actual limit you are hitting

✗ "it sounds impressive"
✗ a single agent with better tool routing would do
```

Most tasks that *look* like they need multiple agents just need a
better prompt and the right tools. Measure first.

## What gets hard

```text
- who decides a subtask is done?
- how do agents share state without a shared context window?
- error propagation: one subagent fails, what happens to the rest?
- cost: N agents means N× the tokens
- debuggability: the timeline becomes a tree, not a list
- loops: agent A delegates to B which delegates back to A
```

That last one is real. You already have `MAX_TOOL_ROUNDS` and
`MAX_DUPLICATE_CALLS` from Phase 2.9 for single-agent loops. Multi-agent
needs the same circuit breakers, one level up.

## The cheap version to try first

Instead of true multi-agent orchestration, give one agent a
`delegate_to_agent` tool. It reuses everything: routing, permissions,
approval, the execution timeline. If that proves insufficient, then
build orchestration.

# V3.2 — Plugin SDK

Let other developers build plugins without reading your codebase.

```text
@agent_hub_plugin(
    key="acme_crm",
    name="Acme CRM",
    version="1.0.0",
)
class AcmeCRM:

    @tool(read_only=True, risk="safe")
    def search_customers(self, query: str) -> list[Customer]:
        """Search customers by name or email."""
        ...

    @tool(read_only=False, risk="high", requires_approval=True)
    def delete_customer(self, customer_id: str) -> None:
        """Permanently delete a customer record."""
        ...
```

The decorator emits MCP tool definitions **with proper annotations** —
which means Phase 2's classifier reads `readOnlyHint` and
`destructiveHint` directly instead of guessing from the verb.

```text
Ship with the SDK:
  - a local test harness (no Agent Hub needed)
  - a validator: schemas, annotations, naming
  - docs generated from the code
  - a template repository
  - a publishing CLI
```

**Prerequisite:** V2.1 custom MCP servers. The SDK is a convenience
layer over a runtime that must already exist.

# V3.3 — Advanced observability

By V3 you need to answer questions about the system as a whole, not
one request.

```text
DISTRIBUTED TRACING (OpenTelemetry)

  HTTP request
   └─ agent turn
       ├─ routing            4ms
       ├─ LLM call          8.2s
       ├─ tool execution
       │   ├─ permission     1ms
       │   ├─ approval      42s   ← waiting for a human
       │   └─ MCP call     421ms
       └─ LLM call          3.1s
```

One trace answers "why did that take a minute?" without correlating
five log files.

```text
PRODUCT ANALYTICS

  which tools are actually used?          → prune the rest
  which routing decisions get overridden? → lexicon gaps
  where do users abandon a turn?          → latency budget
  approval approve/deny ratio             → defaults are wrong if
                                            approval is always "yes"
  cost per user per month                 → pricing
```

That fourth one is a genuine insight: if users approve 99% of
requests, your approval prompts are noise and should be replaced with
per-tool auto-approve rules. If they deny often, your router or your
agent prompt is wrong.

```text
EVALUATION HARNESS

  a fixed set of tasks with known-good outcomes, run on every change
  to routing, prompts, or the model:

    "list my open issues"        → github_list_issues called
    "am i free tomorrow"         → freebusy or list_events called
    "delete everything"          → nothing destructive executes

  Without this, every prompt tweak is a guess.
```

The Phase 2 test suite (`tests/router/test_router.py`) is already the
seed of this. Extend it with live-model runs rather than replacing it.

# V3.5 — Model flexibility

`AI_Agent_Hub.md` calls for an `LLMProvider` interface. Phase 2 already
did this for embeddings (`EmbeddingProvider`) — the same shape applies.

```python
class LLMProvider(Protocol):
    async def chat(
        self,
        messages: list[dict],
        tools: list[dict],
        model: str,
    ) -> LLMResponse: ...
```

```text
Ollama       today, local
OpenAI       gpt-*
Anthropic    claude-*
Google       gemini-*
Groq / OpenRouter
```

## Why it becomes important

```text
- different agents want different models (cheap vs capable)
- customers arrive with a provider they already pay for
- one provider going down should not stop the product
- cost control: route simple turns to a smaller model
```

## Do it properly once

```text
- normalise tool-call formats (every provider differs)
- normalise streaming
- normalise token accounting
- per-provider retry and rate-limit behaviour
- a capability matrix (not every model does tool calling well)
```

`agent/loop.py` currently calls `ollama.chat` directly. That is one
import to replace — and the reason to do it before you have five
providers, not after.

# How to decide what to build

For anything in this document, answer these honestly:

```text
1. Which real user asked for this?
2. What do they do today instead?
3. What breaks if we never build it?
4. What is the smallest version that tests the idea?
5. What ongoing cost does it add, forever?
```

If question 1 has no answer, it is not ready.

# V3 milestone

There is no single milestone here, because there is no single V3.
Instead, the health checks that matter at this stage:

```text
✓ a new engineer ships a change in their first week
✓ an incident is diagnosed from traces alone
✓ a prompt or model change can be evaluated before release
✓ adding an integration needs no core code change
✓ the cost per active user is known and stable
✓ nothing in this document was built without a user asking
```

That last one is the real test.
